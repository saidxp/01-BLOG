## 1. System Architecture Overview

This is a **stateless RESTful backend** serving a blog platform. The application follows a classic **layered architecture**:

```
HTTP Client / Browser / Angular Frontend
        │
        ▼
  ┌─────────────────────────────────┐
  │    Embedded Apache Tomcat       │  ← HTTP/HTTPS server (Spring Boot managed)
  └─────────────────────────────────┘
        │
        ▼
  ┌─────────────────────────────────┐
  │   Spring Security Filter Chain  │  ← JWT extraction → authentication → authorization
  │    JwtAuthenticationFilter      │
  └─────────────────────────────────┘
        │
        ▼
  ┌─────────────────────────────────┐
  │   Spring MVC DispatcherServlet  │  ← Route to @RestController
  └─────────────────────────────────┘
        │
        ▼
  ┌─────────────────────────────────┐
  │   @RestController Layer         │  ← Input validation, authentication extraction
  └─────────────────────────────────┘
        │
        ▼
  ┌─────────────────────────────────┐
  │   @Service Layer                │  ← Business logic, transaction management
  └─────────────────────────────────┘
        │
        ▼
  ┌─────────────────────────────────┐
  │   Spring Data JPA Repositories  │  ← Database queries
  └─────────────────────────────────┘
        │
        ▼
  ┌─────────────────────────────────┐
  │   PostgreSQL Database           │  ← Managed by Flyway migrations
  └─────────────────────────────────┘
```

**Key design decisions:**
- **Cookie-based JWT** — The JWT token is stored in an `httpOnly` cookie named `jwt`, not in `Authorization` headers. This protects against XSS attacks.
- **Stateless sessions** — `SessionCreationPolicy.STATELESS` is enforced; the server never stores session state.
- **Flyway** manages all DDL — `spring.jpa.hibernate.ddl-auto: none`. Schema is version-controlled via SQL migration scripts.
- **WebSocket** (STOMP over SockJS) is used for real-time push notifications only.

## 3. Security Model

### 3.1 Authentication Flow

```
[Client] ──POST /api/auth/login──► [AuthController]
                                        │
                                        ▼
                               [AuthService.login()]
                                        │
                          ┌─── AuthenticationManager.authenticate()
                          │         (DaoAuthenticationProvider)
                          │               │
                          │    UserDetailsServiceImpl.loadUserByUsername()
                          │               │
                          │         [PostgreSQL: users table]
                          │               │
                          │    BCrypt password verification
                          │               │
                          └─► Pair<LoginResponse, JWT token>
                                        │
                          ┌─────────────┘
                          │ Set httpOnly cookie: "jwt"
                          ▼
              [Client receives user data + cookie is stored by browser]
```

### 3.2 JWT Token

- **Library:** `io.jsonwebtoken` (jjwt 0.12.7)
- **Algorithm:** HMAC-SHA (key from `JWT_SECRET` env variable)
- **Expiration:** Configurable via `JWT_EXPIRATION` env var (default: `86400000` ms = **24 hours**)
- **Transport:** `httpOnly` cookie named `jwt`
- **Claims:** Only `subject` (username) is stored in the token

### 3.3 Request Authentication

Every request goes through `JwtAuthenticationFilter` (extends `OncePerRequestFilter`):

```
1. Extract "jwt" cookie from request
2. If cookie absent → pass through (unauthenticated)
3. Parse JWT → extract username
4. If JWT invalid/expired → return 401 via JwtAuthenticationEntryPoint
5. Load user from DB via UserDetailsServiceImpl
6. If user BANNED (account not non-locked) → clear cookie, pass unauthenticated
7. If token valid → inject UsernamePasswordAuthenticationToken into SecurityContext
8. Continue filter chain
```

### 3.4 Authorization Rules

Defined in `SecurityConfig.securityFilterChain()`:

| Pattern | Method | Access |
|---|---|---|
| `/api/auth/**` | ANY | ✅ Public |
| `/error` | ANY | ✅ Public |
| `/api/posts/**` | `GET` | ✅ Public |
| `/api/users/**` | `GET` | ✅ Public |
| `/media/**` | ANY | ✅ Public |
| `/ws/**` | ANY | ✅ Public (WebSocket handshake) |
| `/api/admin/**` | ANY | 🔒 `ROLE_ADMIN` only |
| Everything else | ANY | 🔒 Authenticated users |

### 3.5 User Roles

```java
public enum Role { USER, ADMIN }
public enum UserStatus { ACTIVE, BANNED }
```

- `ADMIN` role grants access to all `/api/admin/**` endpoints.
- `BANNED` status causes the filter to silently clear the cookie and deny access.

### 3.6 Password Storage

Passwords are hashed using **BCrypt** via `BCryptPasswordEncoder`. The raw password is never stored.

### 5.1 Auth Module — `/api/auth`

#### `POST /api/auth/register`
Register a new user account.

**Access:** Public  
**Content-Type:** `application/json`

**Request Body:**
```json
{
  "username": "john_doe",
  "email": "john@example.com",
  "password": "secretPassword"
}
```

> ⚠️ Username and email are **normalized** (trimmed, lowercased) before storage.

**Response:** `201 Created`
```json
{
  "id": 1,
  "username": "john_doe",
  "email": "john@example.com"
}
```

**Side Effects:**
- Creates user record in `users` table with `role=USER`, `status=ACTIVE`
- Sets `httpOnly` cookie `jwt` with 24h expiration

**Errors:**
| Status | Condition |
|---|---|
| `409 Conflict` | Username or email already taken |
| `400 Bad Request` | Validation failure (missing fields, etc.) |

---

#### `POST /api/auth/login`
Authenticate an existing user.

**Access:** Public  
**Content-Type:** `application/json`

**Request Body:**
```json
{
  "identifier": "john_doe",
  "password": "secretPassword"
}
```

> The `identifier` field accepts either **username** or **email**.

**Response:** `200 OK`
```json
{
  "id": 1,
  "username": "john_doe",
  "role": "USER"
}
```

**Side Effects:** Sets `httpOnly` cookie `jwt`

**Errors:**
| Status | Condition |
|---|---|
| `401 Unauthorized` | Wrong credentials |
| `403 Forbidden` | Account is banned |

---

#### `POST /api/auth/logout`
Clear the authentication cookie.

**Access:** Public  
**Response:** `200 OK` (empty body)

**Side Effects:** Sets `jwt` cookie with `maxAge=0` (browser deletes it)

## 6. WebSocket (Real-Time Notifications)

The backend uses **STOMP over SockJS** for pushing real-time notifications to connected clients.

### Connection

```
Endpoint:  ws://localhost:8080/ws  (with SockJS fallback)
Protocol:  STOMP
```

**Allowed Origins:** `http://localhost:4200`, `http://localhost:4000`

### Authentication

The `WebSocketAuthChannelInterceptor` runs on every inbound STOMP message. It extracts the JWT from the STOMP connection headers (same cookie mechanism) and populates the security context for the WebSocket session.

### Subscribe to Notifications

After connecting, a client subscribes to their personal queue:

```javascript
// STOMP client subscription
stompClient.subscribe('/user/queue/notifications', (message) => {
  const notification = JSON.parse(message.body);
  // handle real-time notification
});
```

### Broker Configuration

| Setting | Value |
|---|---|
| Simple in-memory broker prefix | `/queue` |
| Application destination prefix | `/app` |
| User destination prefix | `/user` |

### How It Works

When an event occurs (new like, new subscriber, new comment), the `NotificationService` creates a `Notification` entity, persists it to PostgreSQL, then calls `NotificationWebSocketPublisher.sendTestMessage()` which uses `SimpMessagingTemplate.convertAndSendToUser()` to push a `NotificationDto` to the target user's personal queue.

## 7. Database Schema (Flyway Migrations)

Migrations are applied in order from `classpath:db/migration`. The schema is **never auto-generated** by Hibernate.

| Migration | Description |
|---|---|
| `V1__create_users_table.sql` | `users` table: id, username, email, password_hash, role, status, created_at, updated_at |
| `V2__create_subscriptions_table.sql` | `subscriptions` table: subscriber_id → subscribed_to_id |
| `V3__create_posts_table.sql` | `posts` table: id, author_id (FK), media_url, created_at |
| `V4__create_likes_table.sql` | `likes` table: user_id + post_id (composite unique) |
| `V5__create_comment_table.sql` | `comments` table: id, post_id, user_id, content, created_at |
| `V6__create_notificaiton_table.sql` | `notifications` table: id, recipient_id, type, message, read, created_at |
| `V7__create_report_table.sql` | `reports` table: id, reporter_id, reported_id, post_id (nullable), reason, created_at |

## 9. Cross-Cutting Concerns

### CORS Policy

Configured in `CorsConfig.java`:

| Setting | Value |
|---|---|
| Allowed Origins | `http://localhost:4200`, `http://localhost:4000` |
| Allowed Methods | `GET, POST, PUT, DELETE, PATCH, OPTIONS` |
| Allowed Headers | `*` |
| Allow Credentials | `true` (required for cookie-based auth) |
| Mapped Paths | `/api/**` |

> **Note:** WebSocket endpoint `/ws/**` CORS is configured separately in `WebSocketConfig`.

### Media File Storage

- Interface: `MediaStorageService`
- Implementation: `LocalMediaStorageService` (stores files on disk under `uploads/`)
- Files served via: `WebConfig` which maps `/media/**` to the `uploads/` directory
- Cleanup: `MediaCleanupJob` (scheduled task) removes orphaned files (uploaded but not associated with any post)

### Input Normalization

The `Normalizer` service in the auth module normalizes usernames and emails:
- **Username:** trimmed, lowercased
- **Email:** trimmed, lowercased

This prevents duplicate account creation via case variations.

### Pagination

All list endpoints use **Spring Data Pageable**:
- Default page size varies by endpoint (10 or 20)
- Clients can pass `?page=0&size=10&sort=createdAt,desc`
